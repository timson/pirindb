# Sharding in PirinDB

PirinDB supports horizontal scaling via **sharding**, using **consistent hashing with a ring**. This document explains how sharding is configured, how keys are distributed, and how to safely scale the cluster by adding or removing shards.

---

## Sharding Overview

* PirinDB uses a **consistent hash ring** to map keys to shards.
* Shards are defined statically in the configuration file (`.toml` format).
* Each shard owns multiple **virtual nodes** on the ring to ensure uniform distribution (`1000` virtual nodes per shard).
* Each node in the cluster only manages the data for a single shard but knows about all others.

---

## Configuration

Shard definitions are part of the main configuration file. Each shard must have a unique name, host, port, and gossip port:

```toml
[[shards]]
name = "aleph"
host = "127.0.0.1"
port = 4321
gossipport = 7946

[[shards]]
name = "bet"
host = "127.0.0.1"
port = 4322
gossipport = 7947

[[shards]]
name = "gimel"
host = "127.0.0.1"
port = 4323
gossipport = 7948
#skip = true
```

To **exclude a shard from the current ring**, set `skip = true`. This is useful when phasing out a shard.

---

## Adding Shards

To add new shards:

1. Edit the config file and append the new shard(s).
2. Deploy the new nodes with this updated config.
3. Restart all shard processes so they re-read the configuration and reinitialize the ring.

> On restart, each shard compares the **previous ring hash** (stored on disk) with the new one. If they differ, the shard is marked `out_of_sync`.

---

## Data Read/Write Semantics

* **Writes** always use the new (current) ring.
* **Reads** try the current ring first. If the key is not found, it falls back to the previous ring.
* This dual-ring logic ensures smooth operation during rolling re-shards.

---

## Resharding Data

When the ring topology changes (due to added or removed shards), the data must be **reshuffled**.

To start resharding on a node:

```bash
POST /api/v1/cluster/resharding
```

* This will:

    * Iterate over all local keys.
    * Recalculate their destination shard using the **current ring**.
    * Transfer them to the appropriate shard if needed.
    * Remove the transferred keys from the local store.

After successful resharding, the shard is marked `in_sync` and stores the new ring hash as the reference.

---

## Removing Shards

To remove a shard:

1. **Mark it as skipped** in the config file:

   ```toml
   skip = true
   ```
2. Restart all nodes with this updated config.
3. Run the resharding process on all remaining shards to migrate data away from the skipped shard.
4. After resharding completes, **remove the shard config entirely**.

---
## Clock Safety with HLC
To prevent write conflicts and data loss during concurrent operations and resharding, PirinDB uses a Hybrid Logical Clock (HLC).
* Every write operation is tagged with a timestamp generated by the local HLC.
* Incoming write requests include their HLC in headers.
* Before applying a write, the system compares the local HLC for the key with the incoming one.
  * If the incoming timestamp is older, the write is ignored.
  * If it's newer, the value is stored, and the local HLC is updated.

This mechanism guarantees monotonicity and avoids overwriting newer values with stale data, even under partial network partitions or delayed resharding.
Shards also update HLC on metadata exchange, and PUT/GET/DELETE requests also.

---
## Internals and Guarantees

* Ring hashes are serialized and persisted locally.
* Each ring has a fingerprint hash to detect differences.
* Reads will never fail due to sharding changes, as long as the data has not yet been resharded away.
* Manual resharding provides operational safety and predictability.
